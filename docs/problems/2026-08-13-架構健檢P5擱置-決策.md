# 架構健檢 P5 擱置決策（2026-08-13）

> 背景：20-30 tickets 快速迭代後，使用者要求架構健檢（`/improve-codebase-architecture`）——
> 診斷 5 點＋提案 6 項（P1-P6，按風險低→高）；P1-P4 已實作（commit `9a480b7`＋`6920d19`，
> 590 passed 零回歸）。本文記錄 P5 為何不做。

## P5 內容

`_index_page`（主頁，~375 行＋6 closure）拆成多個頁面區元件（上傳區／引擎卡區／開始按鈕區…）。

## 風險（使用者質詢「高風險還要做?」後的三層分析）

1. **closure state 傳遞**：`staged`／`selected_engine`／`page_select`／各 option inputs 全是
   `index()` local 變數、被內層 closure 捕獲——拆元件＝改 state 流動方式，漏傳/傳錯即行為變。
   P1-P4 皆機械性搬家（純函式／參數收斂），P5 是唯一動 state 流動的一項。
2. **DOM 順序測試敏感**：主頁是 user_simulation 重災區（#16 DOM 順序測試、marker 定位、
   票 19 `lambda eid=eid:` 陷阱）——嵌套層級／順序動一格＝測試一片紅。
3. **重排不減熵**：拆完行數不變、closure 還是 closure——不像 P1-P4 消重複／收知識，無架構收益。

## 決策

**不主動做**，標記擱置。等新功能自然驅動：下次需要共用「引擎卡」或「檔案上傳區」的頁面時，
順手抽元件（`_render_card` 先例——有真實消費端時介面邊界才正確）。
